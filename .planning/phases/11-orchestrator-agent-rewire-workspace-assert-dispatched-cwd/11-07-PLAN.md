<objective>
Close VERIFICATION.md CR-01 (BLOCKER), CR-04 (WARNING), and WR-03 (INFO) — the cluster of gaps caused by `sdk/src/query/workspace-assert-dispatched-cwd.ts:57` doing `safeRealpath(entries[i].path)` against the jj adapter's `WorkspaceInfo.path` field, which on jj carries a workspace NAME (e.g. `"default"`, `"phase-11-subagent-1"`), not an fs path. ## OQ-1: Data-model choice for jj workspace name → fs path resolution

**Decision:** This plan does NOT pre-pick between Option A (narrow on `vcs.kind` inside the verb body) and Option B (extend `WorkspaceInfo` with a `workspacePath?: string` field populated by both backends).

**Option A — narrow on `vcs.kind`:**
- Pro: Smaller blast radius — only `workspace-assert-dispatched-cwd.ts` changes plus possibly a new helper in `sdk/src/vcs/jj/`.
- Pro: Per-call shell-out cost is paid only when this specific verb runs (low — once per agent dispatch).
- Pro: No interface extension — `WorkspaceInfo` stays the same shape; no audit of other callers.
- Con: Adds a `vcs.kind` branch in the verb body — mild violation of the Phase 11 milestone framing ("Workflows never branch on `vcs.kind` for parallel-dispatch reasons"). But the milestone framing scopes to WORKFLOWS, not to internal SDK verbs, and the verb's CONSUMER surface stays backend-opaque.
- Con: If a second consumer of "workspace name → fs path" surfaces later, the resolver gets duplicated.

**Option B — extend `WorkspaceInfo` with `workspacePath?`:**
- Pro: Other consumers automatically get the absolute fs path without re-implementing the resolver.
- Pro: Pushes the asymmetry into the data shape (the field is always populated where the backend can compute it); no `kind` branching at all.
- Pro: Tracks the original verifier-suggested fix shape verbatim.
- Con: Larger blast radius — every `WorkspaceInfo` call site needs auditing (Grep finds at least the jj.ts internal uses and the git.ts list body); some may need their own population logic.
- Con: Forces a per-entry `jj workspace root --name X` call from `parseJjWorkspaceList` (or template extension if jj supports it) — amortized cost across all `workspace.list()` calls, not just this verb's.
- Con: Risk of "do this in jj's parser, but git's already-fs-path stays as-is" leading to subtle null-vs-string handling bugs.

**Verifier recommendation:** Either works; the verifier did not pre-pick. Plan A (this plan) groups CR-01 + CR-03 + CR-04 because they share file-touches; the CR-01 data-model choice is the only contentious bit.
