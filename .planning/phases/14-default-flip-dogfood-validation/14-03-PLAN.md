<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| argv → bash script | Two positional arguments (`<pre-op-id> <tarball-path>`) from the operator's shell. Arg-count guard validates `$#`. |
| `<tarball-path>` → tar utility | `tar -xf <path> -C .` reads the tarball passed as argv. Pre-flight `-f` existence check. |
| `<pre-op-id>` → jj op restore | The op-id is taken as-is and passed to `jj op restore`; jj itself validates op-id format and reports a clear error on unknown ids. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-T-injection | Tampering (shell injection via argv) | bash arg expansion | mitigate | All argv usages are double-quoted (`"$PRE_OP_ID"`, `"$TARBALL_PATH"`) and assigned to named variables before use. No `eval`. No `$@` passed unquoted. Per RESEARCH § Security Domain row "Shell injection via env vars". |
| T-14-T-tarball-traversal | Tampering (path traversal via tarball) | `tar -xf <user-arg> -C .` | accept | The tarball is created by `dogfood-phase-14.sh`'s own `tar cf "${PRE}/planning.tar" .planning/` step (Plan 05) — content-controlled by the same harness, not user input. If an attacker substitutes a malicious tarball at the same path, they already have shell access (out of threat scope). Per RESEARCH § Security Domain row "Path traversal via tarball untar". |
| T-14-T-op-restore | Tampering (op-restore to attacker-controlled op-id) | `jj op restore <user-arg>` | accept | The pre-op-id is captured by `dogfood-phase-14.sh` and persisted into the durable metrics file. Operator-controlled argv; if an attacker controls argv, they already have shell access. Per RESEARCH § Security Domain row "jj op restore to attacker-controlled op-id". |
| T-14-V12-tarball | Files and Resources (V12) | `tar -xf` extract into `.` | mitigate | Extracted into the project root (well-defined boundary per the "must be run from project root" precondition). Caller-controlled cwd; the recovery script does NOT change directory. |
| T-14-Repud-unrelated-work | Repudiation (op-restore reverting unrelated post-dogfood work) | jj op-log restoration | mitigate (documented) | The metrics file's "Recovery Anchor" section (Plan 05) calls this out explicitly: "Operators must save unrelated work before invoking recovery." The script itself does NOT detect or guard against this; that's an operator-responsibility surface. Per RESEARCH § Security Domain row "jj op restore reverting unrelated post-dogfood work". |
