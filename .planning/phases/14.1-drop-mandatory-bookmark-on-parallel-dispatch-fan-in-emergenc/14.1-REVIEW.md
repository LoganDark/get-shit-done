## Summary

PARALLEL-08 implementation surveyed: `ParallelDispatchOpts.mainBookmark: string` → optional `mainBookmarks?: readonly string[]` rename, all-or-nothing per-name validation moved from dispatch to fan-in, two-pass advance loop on jj (`jj bookmark set <name> -r @`) and git (`git update-ref refs/heads/<name> HEAD`) under `!conflicted` gate, CLI bridge repeated-singular `--main-bookmark` accumulator, symmetric removal of the `current-branch` FATAL preflight from both workflow files, and regression-net polarity flip on `CR-03` lint.

The changes are internally consistent and the test coverage closely mirrors the cross-backend symmetry. No security or data-loss defects found. However, several correctness and quality issues warrant attention:

- **The biggest concern (WR-01)** is that validation was moved from dispatch into fan-in but RUNS AFTER significant fan-in side effects (the N-parent `jj new` merge change has already been created at `@` before validation throws). The comment claims "Pass 1: validate every name. ... no side effects yet" but the side effects in question are LOCAL to the advance loop — the merge change itself is already on disk. The "no partial advance" pre-state/post-state assertions in test scenario 3 (jj) verify bookmark advance state but NOT workspace/merge-change state.
- **Backend asymmetry around HEAD/main advance (WR-02):** When the orchestrator IS already checked out on a branch (e.g. `main`), the git fan-in's `git merge --no-ff` implicitly advances that branch as a side effect of the merge, regardless of `mainBookmarks` contents. Passing `mainBookmarks: ['release']` while on `main` will advance BOTH `main` (implicitly) AND `release` (via `update-ref`). The jj backend does not have this side effect because it uses `jj new -r @ -r <p1> ...` which does not advance any bookmark. This violates the cross-backend equivalence the type rename suggests.
- **Dead self-assignment (WR-03)** in `jj/parallel.ts:408`: `surplusBookmarks = []` reassigns to the already-initialized empty array.
- **Test coverage gap (WR-04):** the new `--main-bookmark` CLI plumbing has no test that asserts the parsed flag values arrive on `ParallelDispatchOpts.mainBookmarks` — the only CLI-plumbing test (`cmd-parallel-max-concurrency-cli.test.ts`) records only `maxConcurrency` on the fake adapter. Plumbing for an accumulator with argv-order semantics, no dedup, and zero/one/many flag counts is asserted only indirectly via integration tests that go through a real adapter.

Info-tier items below cover stale comments, validator-prefix carry-over, and a documented permanent no-op in the EXPECTED_BRANCH drift guard (pre-existing, deliberately preserved per Pitfall 6 commentary).

## Warnings

### WR-01: Validation moved into fan-in runs AFTER the N-parent merge side effect

**File:** `sdk/src/vcs/jj/parallel.ts:428-434`
**Issue:** Phase 14.1 retired the up-front `validateMainBookmark` from `performJjParallelDispatch` (acknowledged at :186-189) and moved per-name validation into `performJjParallelFanIn` as Pass 1 at :432. However, by the time Pass 1 runs:

1. `vcs.workspace.list()` has already been queried (line 314-322).
2. The N-parent `jj new -r @ -r <p1> -r <p2> ...` has already executed at line 345, creating a new merge change at `@`.
3. The `conflicts()` revset probe has already run at line 376.
4. `resolveChangeId` has already returned a change_id for the new merge.

The body comment "Pass 1: validate every name. Throws on first invalid; no side effects yet" (:430-431) is misleading. It is locally accurate within the advance loop, but globally the side-effects of the surrounding fan-in have already landed. Throwing here leaves the user with a new merge change at `@`, no bookmark advance, and ambiguous resolution path. The same defect mirrors on the git side: `git/parallel.ts:486-490` performs the full per-branch merge loop AND STEP 2 crashed-agent classification before `validateRefname` runs.

Test scenario 3 (jj at :629-699 and git at :908-958) pins "no partial advance of bookmarks" but does NOT assert "no merge change created at @" / "no per-branch merge committed". A regression that violates the no-partial-merge invariant would slip past the gate.

**Fix:** Either (a) restore a validation Pass 0 inside `performJjParallelDispatch` / `performGitParallelDispatch` (the same place that already validates `agentId`), so invalid names rejected up front — at the cost of duplicating validation when fan-in is called via CLI; or (b) keep validation in fan-in but call it BEFORE the N-parent `jj new` / per-branch git merge loop. Option (b) is cleaner; option (a) matches the original Phase 9/10 invariant the comment block at :186-189 retired.

```ts
// Option (b): validate at the top of performJjParallelFanIn, before workspace.list().
export function performJjParallelFanIn(...) {
  const mainBookmarks = handle.mainBookmarks ?? [];
  // Validate FIRST, before any side effect.
  for (const name of mainBookmarks) validateMainBookmark(name);
  const phaseTag = ...;
  // ... existing body
}
```

### WR-02: Cross-backend asymmetry — git `merge --no-ff` advances HEAD-tracked branch implicitly, jj N-parent `jj new` does not

**File:** `sdk/src/vcs/git/parallel.ts:386-422` (vs `sdk/src/vcs/jj/parallel.ts:335-350`)
**Issue:** The new `mainBookmarks` contract is presented as cross-backend symmetric — empty list ↔ skip the per-name advance; non-empty list ↔ advance each name. On jj this is exact: `jj new -r @ -r <p>...` does not touch any bookmark, and only the explicit `jj bookmark set <name> -r @` advances anything. On git, by contrast, the fan-in body uses `git merge --no-ff <agentBookmark>` (line 390), which IMPLICITLY advances whatever branch is currently checked out — typically the project default branch (e.g. `main`). This means:

- `mainBookmarks: []` on git with HEAD checked out on `main` still ADVANCES `main` as a side effect of the merge — directly contradicting the docstring at git/parallel.ts:468-469 ("Empty/omitted list → SKIP (detached-HEAD git is a first-class dispatch state — the merge already landed into HEAD itself via `merge --no-ff`)"). The docstring elides the case where HEAD is NOT detached.
- `mainBookmarks: ['release']` on git with HEAD on `main` advances BOTH `main` (implicit) AND `release` (explicit update-ref). A jj caller passing `mainBookmarks: ['release']` with `@` pointing at a bookmark `main` would advance ONLY `release`; `main` would lag.

The git-side test for this scenario (scenario 2 at git/parallel.test.ts:840-890) does NOT probe post-state of `main` to verify it stayed at the seed — it only asserts `release` and `integration` reach HEAD. The jj-side counterpart at jj/parallel.test.ts:562-611 has nothing to assert (no implicit advance can happen).

This asymmetry leaks into user-visible semantics: writing portable orchestration that depends on "advance ONLY these names" requires the caller to know they're on git AND detach HEAD before fan-in, OR pass the currently-checked-out branch in the `mainBookmarks` list to mirror its implicit advance back into the contract.

**Fix:** Either (a) update the git-side scenario 1 detached-HEAD test to also include a non-detached scenario that asserts `main` advances even with empty `mainBookmarks` (documenting the leak), OR (b) on the git side, detach HEAD before the per-branch merge loop and re-attach only when the user explicitly lists the current branch in `mainBookmarks`, OR (c) restrict `git merge --no-ff` to operate on a temporary ref so the implicit branch advance never occurs. (a) is the cheapest; (c) is the most user-friendly but requires reworking the merge protocol significantly.

### WR-03: Dead self-assignment to `surplusBookmarks` in jj fan-in conflicted branch

**File:** `sdk/src/vcs/jj/parallel.ts:389,408`
**Issue:** `let surplusBookmarks: string[] = [];` at line 389 initializes the array to empty. Line 408 reassigns it to `[]` again on the `conflicted` branch — a no-op. The `let` qualifier is now never meaningful since `surplusBookmarks` is never assigned a non-empty value anywhere in the function body (Phase 11 D-02 retired the eager bookmark plumbing that populated it). The variable could become `const` and the reassignment removed.

```ts
// Before
let surplusBookmarks: string[] = [];
// ...
if (conflicted) {
  // ...
  surplusBookmarks = [];   // <-- dead
}
// ...
return Object.freeze({
  // ...
  surplusBookmarks: Object.freeze(surplusBookmarks.slice()) as readonly string[],
});

// After
const surplusBookmarks: readonly string[] = [];
// ...
if (conflicted) {
  // (no reassignment needed)
}
// ...
return Object.freeze({
  // ...
  surplusBookmarks: Object.freeze(surplusBookmarks.slice()) as readonly string[],
});
```

This is a quality issue, not a behavior issue — but the self-assignment invites confusion ("why is this here?") and the explanatory comment at :406-407 only hides the dead code.

### WR-04: No direct test that `--main-bookmark` CLI flags arrive on `ParallelDispatchOpts.mainBookmarks`

**File:** `sdk/src/vcs/__tests__/cmd-parallel-max-concurrency-cli.test.ts:43-56`
**Issue:** The fake adapter installed via `vi.mock` records only `{ maxConcurrency }` from the dispatch opts (line 43). The Phase 14.1 CLI bridge plumbing for `--main-bookmark` — repeated-singular accumulator, argv order, no dedup, zero-flag-yields-empty-list behavior — has NO test that asserts the parsed flag values arrive on `mainBookmarks` in the adapter call. The only tests that exercise multi-name advance behavior (`cmd-parallel-jj.test.ts` SC5 scenario 2, lines 562-611; `cmd-parallel-git.test.ts` SC5 scenario 2, lines 840-890) go through a real adapter and call `vcs.workspace.parallel.dispatch({mainBookmarks: [...]}` programmatically — they bypass the CLI bridge entirely.

A defect like "CLI bridge drops the second `--main-bookmark` flag silently" would pass every test in the patch. The bridge's `args[i + 1]` truthiness check at line 70 could similarly be a typo (`args[i + 2]`?) without breaking any test.

**Fix:** Extend `cmd-parallel-max-concurrency-cli.test.ts` to record `mainBookmarks` too, then add 2-3 cases:
```ts
// Zero flags → empty array
await workspaceParallelDispatchQuery(['--phase', '11', '--plan', plan], cwd);
expect(recordedDispatchOpts[0].mainBookmarks).toEqual([]);

// One flag → single-entry array

// Two flags, argv-order preserved

// Duplicates preserved (no dedup)
await workspaceParallelDispatchQuery(['--phase', '11', '--main-bookmark', 'main', '--main-bookmark', 'main', '--plan', plan], cwd);
expect(recordedDispatchOpts[0].mainBookmarks).toEqual(['main', 'main']);
```

These pin the documented behavior at the CLI bridge layer where it lives — without them, the CLI contract is asserted only transitively.

### IN-01: Pre-existing — `EXPECTED_BRANCH` capture in workflows returns empty for all jj backends and detached-HEAD git, making the fan-in drift guard a permanent no-op

**File:** `get-shit-done/workflows/quick.md:673`, `get-shit-done/workflows/execute-phase.md:535`
**Issue:** The workflows capture `EXPECTED_BRANCH=$(gsd-sdk query current-branch --cwd . --pick branch)`. The `current-branch` handler at `sdk/src/query/current-branch.ts:29-34` returns `{ ok: true, bookmarks }` — a string array (per Phase 2.1 D-15 contract on `currentBookmarks()`). There is no `branch` field; `--pick branch` calls `extractField(data, 'branch')` which returns `undefined`, surfaced as empty stdout. So `EXPECTED_BRANCH` is ALWAYS empty regardless of bookmark state.

The downstream drift guard at quick.md:769 / execute-phase.md:769 (`[ -z "${EXPECTED_BRANCH:-}" ] || [ "$ORCH_BRANCH" = "$EXPECTED_BRANCH" ] || { ... FATAL ... }`) short-circuits on `-z "$EXPECTED_BRANCH"` and never fires the FATAL. The comments at quick.md:670-672 and execute-phase.md:532-534 acknowledge this ("gracefully degrades to a no-op when empty per Pitfall 6"), so this is intentionally preserved behavior — but the guard is permanently disabled, and the `#3174-class drift` it claims to protect against can occur without detection.

This is NOT a Phase 14.1 regression — it pre-dates this phase. Phase 14.1 just preserved the no-op. Out of scope for this review per context notes (`current-branch --pick branch` is not in the 14.1 changeset), but worth surfacing because the comment explicitly references "Pitfall 6" without defining it inline, and a reader following the trail to validate the comment may be misled into thinking the guard works.

**Fix (out of scope but documented):** Either (a) change `--pick branch` to `--pick 'bookmarks[0]'` (or similar) so the guard receives the active bookmark name, OR (b) drop `EXPECTED_BRANCH` and the downstream guard entirely as dead code. Option (a) is correct-by-construction; option (b) matches what the code actually does today.

### IN-03: validateRefname error messages still use `expr.bookmark:` prefix when called from git/parallel.ts

### IN-04: Test scenario 3 (all-or-nothing) does not include a probe that the merge change at `@` was rolled back

**File:** `sdk/src/vcs/__tests__/cmd-parallel-jj.test.ts:629-699`, `sdk/src/vcs/__tests__/cmd-parallel-git.test.ts:908-958`
**Issue:** Both SC5 scenario 3 tests assert that bookmarks named in `mainBookmarks` were not advanced on validation throw (the pre-state probe of `present(valid-name)` returning empty matches the post-state probe). But neither test asserts the load-bearing claim "no side effects yet" from jj/parallel.ts:430-431 / git/parallel.ts ~485 — specifically, neither probes whether:

- The N-parent `jj new` merge change at `@` was created (jj) — `jj log -r '@-' -T 'parents.map(|p| p.change_id())'` would expose the N parents if the merge landed before the throw.
- agent-1's per-branch `git merge --no-ff` commit was created before the throw (git) — `git log --oneline HEAD` would show the merge commit even after the throw.

This is the test-side mirror of WR-01. Adding these probes turns the SC5 scenario 3 into a true "no side effects" assertion — without them, the test only proves "no advance"; refactoring the body to add an early side-effect would not regress the test.

**Fix:** Extend SC5 scenario 3 (both files) with:
```ts
// After expect(() => fanIn(...)).toThrow(...)
const post@parents = execSync(`jj log -r @ -T 'parents.map(|p| p.change_id())'`, ...).trim();
expect(post@parents).not.toContain(/* expected parent IDs */);  // assert merge change at @ was NOT created

// git side:
const headAfter = execSync('git rev-parse HEAD', { cwd: dir }).toString().trim();
expect(headAfter).toBe(headBeforeFanIn);  // assert no merge commit landed
```
