## Summary

Phase 14.1 is a tight surface-area revision: drop the required `mainBookmark: string` field on `ParallelDispatchOpts` / `ParallelDispatchHandle` and replace it with optional `mainBookmarks?: readonly string[]` (default `[]` → no advance). All the locked decisions live in CONTEXT.md (CF-01..08, D-01..04); this research verifies the cited insertion-site line numbers against live code, surveys existing test idioms, confirms the two-pass validate-then-mutate idiom is already established in the codebase (jj/parallel.ts:182-188 W1 pattern), confirms the branch-drift guard at line 766 of both workflows is already safe under empty `EXPECTED_BRANCH` (`[ -z "${EXPECTED_BRANCH:-}" ] || ...` short-circuits to success), and surfaces three additional touch sites CONTEXT.md does not name: the legacy CJS shim `get-shit-done/bin/lib/worktree-safety.cjs:404-421` (`reconstructHandleFromLegacyPlan`), the stall-surveillance probe at execute-phase.md:719 that consumes `EXPECTED_BRANCH` in `--range`, and four legacy test files that reference the snake_case `main_bookmark` manifest field.

Primary recommendation: execute the locked single-plan / single-wave structure exactly as specified in CONTEXT.md `## Specific Ideas`. Use the W1 pattern from `jj/parallel.ts:182-188` as the template for the new all-or-nothing pre-validation loop. For the empty-list dispatch+fan-in scenarios, the existing `setupJjRepo` already creates a bookmark-less working copy (no `jj bookmark create main` in the setup) — no new fixture needed beyond a `git checkout --detach HEAD` line on the git side.

### Pattern 1: Two-pass validate-then-mutate (all-or-nothing)

**What:** Iterate the input list twice — pass 1 validates every entry, pass 2 mutates state. Throwing in pass 1 leaves the world unmodified.

**When to use:** When a list of operations must succeed as a unit and partial-progress would corrupt state.

**Example (existing precedent at `sdk/src/vcs/jj/parallel.ts:178-188`):**

```typescript
// Source: sdk/src/vcs/jj/parallel.ts:178-188 (W1 pattern, Phase 9)
// W1: validate every agentId BEFORE any side effect that depends on it.
// `createPhaseStructure` is idempotent (marker bookmarks) so even if a
// retry follows a validation failure, the next attempt won't double-create
// the parent/merge slot.
for (const item of plan) {
    validateAgentId(item.agentId);
}

// Validate main bookmark up-front so a late fanIn failure can't leak a
// non-conformant name into the handle.
validateMainBookmark(mainBookmark);
```

**Same pattern applied to the new mainBookmarks loop (planned, this phase):**

```typescript
// In performJjParallelFanIn clean path (replaces lines 409-419):
if (handle.mainBookmarks && handle.mainBookmarks.length > 0) {
    // Pass 1: validate every name. Throws on first invalid; zero side effects yet.
    for (const name of handle.mainBookmarks) {
        validateMainBookmark(name);
    }
    // Pass 2: advance each. JSDoc must note: throw on first failure leaves
    // partial state if name K fails after names 1..K-1 advanced. Atomic
    // rollback is deferred (Discretion note).
    for (const name of handle.mainBookmarks) {
        const setArgs = [
            ...jjArgvFlags(mainRepoRoot),
            'bookmark', 'set', name, '-r', '@',
        ];
        const setRes = vcsExec(mainRepoRoot, 'jj', setArgs);
        if (setRes.exitCode !== 0) {
            throw new Error(
                `parallel.fanIn: main-bookmark advance (${name}) failed: ${setRes.stderr || setRes.stdout}`,
            );
        }
    }
}
// When empty/omitted: skip both loops entirely. Merge already landed at @
// via the N-parent `jj new` at line 341.
```

### Pattern 2: Conditional opt-in behavior (skip-when-empty)

**What:** A non-empty list triggers behavior; an empty list collapses to no-op. Precedent: Phase 11 D-02 `surplusBookmarks: []` default — the contract preserves the field but its empty state means "skip the operation entirely."

**When to use:** When a previously-mandatory step needs to become optional without API churn for callers that DO want the behavior.

**Example (in CONTEXT.md CF-02 + Phase 11 D-02 precedent):**

```typescript
// jj-side fan-in clean path: structural skip
if (handle.mainBookmarks && handle.mainBookmarks.length > 0) {
    // …two-pass validate + advance…
}
// else: no bookmark mutation. Merge change at @ is the only effect of fan-in.
```

**What:** When two workflow markdown files have the same defensive guard, ANY edit (add OR remove) must touch both files in lockstep. The lint test asserts byte-equivalence as a drift guard.

**When to use:** Whenever `execute-phase.md` and `quick.md` share a structural block (they both dispatch through `workspace.parallel.dispatch`).

### Anti-Patterns to Avoid

- **One-pass interleaved validate-and-mutate** for the `mainBookmarks` loop: defeats the all-or-nothing contract in CF-02. If name 2 is invalid but name 1 was already advanced, the world is dirty AND the caller gets a confusing late-failure stack trace.
- **Deleting `validateMainBookmark` and inlining the regex** in the new loop: adds churn for zero LOC saved (Discretion item recommends KEEP).
- **Converting `--main-bookmark` to a new flag token** (e.g., `--main-bookmarks`): D-02 LOCKED against. Refnames forbid both whitespace and commas, so the singular-repeated form has no future delimiter clash.
- **Touching `WorkspaceMergeOpts.mainBookmark`** at `sdk/src/vcs/types.ts:226`: D-03 LOCKED out of scope. SC1's ":226" citation is a typo. The MERGE-08 deferred entry documents the asymmetry as deliberate.
- **Leaving the legacy CJS shim `reconstructHandleFromLegacyPlan` writing `mainBookmark` to a no-longer-existing field**: see Pitfall 4 below — the shim at `get-shit-done/bin/lib/worktree-safety.cjs:404-421` writes `mainBookmark: entries[0]?.main_bookmark ?? ''` into the reconstructed Handle. After the field is removed, this assignment silently dies in TSC because the shim is `.cjs`. The shim has no production callers (only test callers), but for completeness the planner should at minimum decide: (a) leave the orphaned field write (harmless on .cjs runtime), or (b) drop the line for parity with the new Handle shape.
- **Asserting the FATAL preflight is PRESENT** in either workflow after this phase: the existing CR-03 lint at `tests/quick-md-parallel-dispatch.test.cjs:87-94` MUST flip polarity (`assert.match` → `assert.doesNotMatch`) per D-01.

## Common Pitfalls

### Pitfall 1: CONTEXT.md cited line-number drift on jj/parallel.ts

**What goes wrong:** CONTEXT.md cites `sdk/src/vcs/jj/parallel.ts:409-417` for the fan-in clean-path advance block; the actual block runs through line 419 (closing brace at 418, blank at 419). Minor — but if the planner copy-pastes the citation into the plan's `must_haves` without rechecking, the diff hunk may miss a line.

**Why it happens:** Line numbers in CONTEXT.md are snapshots from the day the context was gathered (2026-05-24). Even a single import-line edit upstream would shift these.

**How to avoid:** Planner re-greps each cited line range before writing the plan. Use `grep -n 'validateMainBookmark\|bookmark.*set' sdk/src/vcs/jj/parallel.ts` to locate the actual current span rather than copying the citation as gospel.

**Warning signs:** Plan `action` text says "edit lines X-Y" and the line numbers don't fall on natural block boundaries (e.g., end on `}` or blank line).
